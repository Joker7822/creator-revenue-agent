# Staging Release Rehearsal

This repository automates a staging rehearsal of the real release path:

```text
semantic release tag
  -> Release Image
  -> GHCR immutable image publish
  -> provenance + CycloneDX SBOM attestations
  -> Verify Release Promotion
  -> staging migration
  -> staging Kubernetes rollout
  -> runtime digest verification
  -> checksummed rollout evidence
```

The rehearsal intentionally consumes the same release image and the same
Promotion Gate used for production. It does not rebuild or retag the image.

## Trigger

The workflow is:

```text
.github/workflows/staging-release-rehearsal.yml
```

It starts only after the `Release Image` workflow completes successfully.
That release workflow is itself triggered by a real semantic `v*` tag.

The rehearsal then binds all later steps to the triggering release run:

- the triggering repository must be this repository
- the triggering event must be a push
- the triggering commit must still be an ancestor of `main`
- exactly one unexpired `release-evidence-v*` artifact must exist
- release evidence checksums must pass
- the release tag must resolve to the same source commit
- the image must be the exact GHCR `@sha256:` reference in the release
  evidence

This prevents an operator-supplied mutable tag from entering staging CD.

## Promotion Gate

`.github/workflows/promote.yml` is reusable through `workflow_call`.

Manual dispatch remains production-only. The staging rehearsal calls the
same workflow with:

```text
target_environment: staging
```

The gate still verifies:

- GitHub build provenance for the exact OCI digest
- signer workflow identity (`.github/workflows/release.yml`)
- release tag source ref
- source commit digest
- no self-hosted-runner attestation
- CycloneDX SBOM attestation for the same image digest
- immutable Kubernetes image rendering
- Kubernetes hardening invariants
- Kubernetes schema validity
- checksummed promotion evidence

The rollout job consumes only the resulting
`verified-promotion-<release-tag>` artifact.

## Required GitHub staging environment

Create a GitHub Environment named:

```text
staging
```

The workflow uses environment-scoped settings so cluster credentials and
non-secret staging identity are not stored in the repository.

### Secret

Configure exactly one kubeconfig secret:

```text
KUBECONFIG_B64
```

It must contain the base64 encoding of a kubeconfig whose selected context
has only the Kubernetes permissions needed for this deployment.

The workflow validates the selected context and API server before any
migration or application apply.

### Variables

Configure:

```text
KUBE_CONTEXT
KUBE_SERVER
K8S_NAMESPACE
SERVICE_JWT_ACTIVE_KID
AUDIT_HASH_ACTIVE_KID
AUDIT_ANCHOR_BASE_URL
AUDIT_ANCHOR_NAMESPACE
```

A typical namespace is:

```text
creator-revenue-agent-staging
```

`KUBE_SERVER` must exactly match the API server in the selected kubeconfig
context. `AUDIT_ANCHOR_BASE_URL` must be HTTPS and must not embed
credentials.

If the `staging` environment uses deployment protection rules, those rules
must pass before the Promotion Gate or rollout can proceed.

## Cluster prerequisites

The staging namespace must exist before the first rehearsal because the
application Secret is deliberately not generated by GitHub Actions.

Provision this Secret in the staging namespace:

```text
creator-revenue-agent-secrets
```

Required keys:

```text
database_url
service_jwt_keys_json
verification_webhook_keys_json
audit_hash_keys_json
audit_anchor_token
audit_anchor_receipt_keys_json
```

Use staging-only credentials and external dependencies. Never copy
production database, JWT, webhook, audit, or anchor credentials into the
staging environment.

The values configured through:

```text
SERVICE_JWT_ACTIVE_KID
AUDIT_HASH_ACTIVE_KID
```

must exist in their corresponding staging key rings. Otherwise `/ready`
will correctly remain unhealthy.

The Kubernetes principal in `KUBECONFIG_B64` should have the minimum
namespace-scoped permissions required to:

- read the namespace
- read only the staging application Secret metadata/data keys
- create/delete/get/watch the migration Job and Pods/logs needed for failure
  diagnosis
- apply the checked-in ServiceAccount, ConfigMap, Deployment, Service,
  PodDisruptionBudget, HorizontalPodAutoscaler, and NetworkPolicy
- get/watch the resulting Deployment and Pods

Namespace creation is not required by the workflow.

## Staging manifest derivation

The checked-in Kubernetes base remains production-oriented and therefore
contains production safety settings plus environment placeholders.

`scripts/render_staging_manifests.py` derives the staging bundle only after
the Promotion Gate succeeds. It changes only:

```text
Namespace metadata.name
kustomization namespace
SERVICE_JWT_ACTIVE_KID
AUDIT_HASH_ACTIVE_KID
AUDIT_ANCHOR_BASE_URL
AUDIT_ANCHOR_NAMESPACE
```

It deliberately retains:

```text
APP_ENV=production
```

This makes staging exercise the production configuration checks rather than
silently weakening them.

The renderer also requires both the Deployment and migration Job to retain
the exact attested `@sha256:` image and regenerates `SHA256SUMS` after the
environment-specific transformation.

## Rollout sequence

For each successful real release tag, the staging workflow performs:

1. acquire and checksum the release evidence from the triggering run
2. bind tag, source commit, and image digest
3. execute the reusable Promotion Gate
4. checksum the Promotion Gate output
5. derive and revalidate the staging Kubernetes bundle
6. validate the exact kubeconfig context and API server
7. validate the required Secret key contract without logging secret values
8. replace and run the one-shot Alembic migration Job
9. require migration completion
10. apply the staging Kustomize application
11. require Deployment rollout and Pod readiness
12. require both the Deployment image and running container `imageID` values
    to match the attested sha256 digest

A failed migration prevents the application rollout.

## Evidence

Every successful rehearsal uploads:

```text
staging-rehearsal-<release-tag>
```

with 90-day retention.

It contains:

```text
staging-kubernetes/
staging-application.yaml
staging-application.yaml.sha256
staging-rollout-evidence.json
staging-rollout-evidence.json.sha256
```

The rollout evidence records:

- release tag
- source commit
- immutable image reference
- Kubernetes context and API server identity
- staging namespace
- Deployment UID and generations
- desired and ready replica counts
- runtime container image IDs
- SHA-256 of Promotion Gate evidence
- SHA-256 of the final staging manifest
- UTC generation timestamp

This provides a direct audit trail from the real release tag through the
running staging digest.

## First rehearsal

After this workflow is merged to `main`:

1. configure the `staging` GitHub Environment
2. provision the staging namespace and application Secret
3. verify the kubeconfig RBAC is namespace-scoped
4. push a real semantic release tag such as `vX.Y.Z`
5. watch `Release Image`
6. watch `Staging Release Rehearsal`
7. retain the generated release, promotion, and staging evidence artifacts

Do not create a synthetic image or bypass the Promotion Gate for the
rehearsal; the purpose is to exercise the same release identity that can
later be promoted to production.
